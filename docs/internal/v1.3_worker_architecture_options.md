# AIVOICE v1.3 — Worker Placement Architecture Options

> Phase：**2-1**（架构比较，不实现）  
> 日期：2026-07-27  
> 输入：`aivoice_v1.3_async_worker_phase1_analysis.md`  
> 约束：未写代码；未改 CoverService / Pipeline / Skill

---

## 1. 当前架构回顾

```text
飞书 → Hermes Gateway → Hermes Agent
         → aivoice-cover Skill（terminal）
              → aivoice_cover.py
                   → CoverService.submit / status / result
                        →（同进程 ThreadPool max_workers=1）
                        → PipelineAdapter → Pipeline
                             → UVR → SVC → Mixer → Export
```

关系要点：

| 组件 | 角色 |
|---|---|
| **Hermes** | 消息与 Agent；不拥有翻唱计算 |
| **Skill / aivoice_cover.py** | 短契约入口，但**当前会阻塞轮询到终态** |
| **CoverService** | 已有 submit/status/result 外观；JobStore **仅内存** |
| **Pipeline** | 同步重计算边界；不应被 Worker「钻进去」改写 |

阻塞根因：**执行宿主与 Hermes tool 进程绑定**，而非缺少 `job_id`。

## 2. Worker 部署位置方案

### Option A — 独立 Worker 进程

```text
Hermes Agent
    │ 短调用：enqueue / submit-meta
    ▼
Skill（aivoice_cover.py 变「只投递」）
    │
    ▼
Durable JobStore（文件/SQLite…）
    │
    ▼
【常驻】Worker 进程
    │
    ▼
CoverService（或 Adapter.run 封装）
    │
    ▼
Pipeline → UVR / SVC / …
    │
    ▼
写回 JobStore + 通知钩子 → Hermes/飞书再推送
```

**优点**

- Hermes tool **秒级返回**（拿到 `job_id` / queued），符合产品目标。
- 进程边界清晰：Agent 崩溃 / 会话结束不影响已在跑的翻唱。
- 单卡互斥可集中在 Worker（全局一槽），优于「每次 Skill 自建 CoverService」。
- 与 Phase 1 结论一致：Worker **夹在 Skill 与 Cover 执行栈之间**。
- 可逐步做：先文件 JobStore + 轮询通知，再 cro n/Gateway 推送。

**缺点**

- 需运维一个常驻进程（Windows：开机脚本 / 任务计划 / 与 Hermes 一并启动）。
- 需定义投递协议（JSON 队列目录、命名管道、本地 HTTP 二选一）。
- 「完成后谁发飞书」要单独设计（Worker 调 Hermes CLI、写 outbox、或 Skill 侧短轮询 job——仍比堵满 UVR 好）。

**适合程度**：**高** — 最贴「个人工作站 + 飞书长任务」问题本质。

---

### Option B — CoverService 内部 Worker

```text
Skill 仍调用 CoverService
CoverService 内：
  - 持久化 JobStore
  - 后台线程/进程池「升级」为真 Worker
```

**优点**

- API 表面可几乎不变（仍 submit/status/result）。
- 改动面名义上集中在 cover 层。

**缺点 / 风险**

- **只要 Skill 进程退出，内嵌线程池与内存态仍死**——除非把 CoverService 放进**另一个常驻进程**，那实质滑向 Option A/C。
- 若坚持「Skill 进程内加强 CoverService」：无法解决 Hermes 长等待，只是把轮询写得更漂亮。
- 易踩边界：为了「持久化」改 CoverService 核心，与「不改执行逻辑」冲突风险高。
- GUI 同步 `run()` 与飞书异步路径耦合在同一类里，演进变脏。

**适合程度**：**低（作为唯一方案）**；最多作为 A 的库内实现细节（常驻进程里 new CoverService）。

---

### Option C — HTTP Job Service（FastAPI / 现有 Flask 扩展）

```text
Hermes Skill
    │ HTTP POST /jobs
    ▼
本地 Job HTTP 服务（常驻）
    │
    ▼
CoverService / Adapter → Pipeline
```

**优点**

- 契约清晰：REST `POST /jobs`、`GET /jobs/{id}`、`GET /jobs/{id}/result`。
- 多客户端友好（未来 GUI/脚本/第二设备可共用）。
- 与「独立 Worker」可合一：HTTP 只是投递面，后面仍是单 Worker 消费。

**缺点**

- 本机多一层服务与端口/防火墙心智负担。
- 现有 Flask `server/api.py` 是同步翻唱 UI，**不能直接当 Job API**；需新表面，避免搅乱 GUI Web。
- 单用户飞书场景下，HTTP 收益有限——文件队列往往更简单。
- 鉴权/本机绑定要处理（至少 bind 127.0.0.1）。

**适合程度**：**中** — 架构正确，但对「当前一人一机」略重；可作为 A 的演进形态。

## 3. Windows 个人 AI 工作站场景分析

| 条件 | 含义 |
|---|---|
| Windows 11 + RTX 4060 Laptop 8GB | 单卡；UVR DirectML + SVC CUDA 已吃满显存峰值；**必须全局串行** |
| Hermes 飞书 Gateway | 已常驻；用户期望「发完就能走」 |
| 单用户 | 无需分布式队列、多租户、云弹性 |
| 目标 | 体感异步，而非平台级 Job 系统 |

方案对照：

| 方案 | 是否解决 Hermes 阻塞 | 运维成本 | 与单卡串行 | 过度设计风险 |
|---|---|---|---|---|
| **A 独立 Worker** | ✅ | 中（一个常驻进程） | ✅ 易做全局锁 | 低 |
| **B 仅加强 CoverService** | ❌（除非变相常驻） | 低但无效 | 弱 | 中（边界模糊） |
| **C HTTP Job Service** | ✅ | 中高 | ✅ | 中高（单用户偏重） |

**场景结论：** 优先 **Option A**；若日后要 GUI/多脚本共用同一队列，再给 A 加 **本地 HTTP 门面（偏 C）**，而不是一上来上完整 Job 平台。

---

## 4. 推荐架构

**推荐：Option A — 独立 Worker 进程 + 持久化 JobStore（本机）。**

推荐形态（仍属架构，非实现）：

```text
[短] Skill：解析/搜歌/选曲完成后 → enqueue(job 元数据) → 立即回「已排队」
[常驻] Worker：单线程消费 → 调用现有 Cover 执行栈 → 更新 JobStore
[通知] 完成 outbox / Gateway 钩子 → 飞书推送文案 + cover.mp3
```

投递介质（后续 Phase 再定）：目录队列或 SQLite 均可；**不默认上 Redis/云队列**。

不推荐单独以 B 作为产品方案；C 作为 A 的可选 API 外壳，而非当前必选项。

## 5. 与现有模块边界

### 保持稳定（不重写）

| 模块 | 说明 |
|---|---|
| **Pipeline** | 同步编排核心不动 |
| **UVR / SVC / Mixer** | 子进程与模型路径不动 |
| **GUI** | 继续 `CoverService.run` 同步路径 |
| **CoverService 执行逻辑** | `_execute_job` → `PipelineAdapter.run` 保持；Worker **调用**它，不拆它 |

### 预期新增（实现阶段才落地）

| 组件 | 职责 |
|---|---|
| **Durable JobStore** | 跨进程保存 queued/running/completed/failed + 路径 |
| **Enqueue API / 队列投递** | Skill 短写：job 请求落盘或入队 |
| **Worker 常驻进程** | 单槽消费、调 Cover 执行、写回状态 |
| **Completion notifier / outbox** | 完成后通知飞书（或供 Hermes 短查后发送） |
| **Skill 行为收缩** | submit/enqueue 后返回；可选极短确认，不再 600s 轮询堵死 |
| **（可选）本地 Job HTTP** | 给 A 加 REST 门面，非 P0 |

### 明确不放进 Worker 内的东西

- 不把 Hermes Agent 逻辑搬进 Worker  
- 不在 Worker 内重写选歌 UX（仍属 Skill / session）  
- 不把 GUI 事件循环绑到 Worker  

---

## 6. Phase 2-1 一句话

在 Windows 单用户 + 飞书场景下，**独立常驻 Worker + 持久化 JobStore（Option A）** 是放置位置的正解；CoverService 内卷线程（B）解决不了进程绑定，HTTP Job Service（C）正确但对本阶段偏重，宜作 A 的后续外壳。
